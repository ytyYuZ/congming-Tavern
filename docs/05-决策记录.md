## ADR-001 · 不 fork SillyTavern，只兼容其数据格式

- 状态：已定
- 决策：自建前端；兼容角色卡 V2/V3、世界书、Prompt 预设、`chat.jsonl`；可选把 ST 后端作为一个 Provider
- 理由：ST 前端是无框架大型单页，UI 重构成本高于重写体验层；上游迭代快，fork 后长期跟进成本高
- 影响：F9、架构 D1；需自研 Prompt 引擎
- 详见：`docs/02-技术架构.md` D1

## ADR-002 · 多端形态与优先级

- 状态：已定
- 决策：Web/PWA 一等公民 → 桌面（Tauri 2）→ 移动（响应式 PWA 优先）
- 理由：一套 UI 代码覆盖三端；避免过早承担原生构建链成本
- 影响：F10、D3、R2

## ADR-003 · 不做后端，BYO-Key + 可选轻量代理

- 状态：已定
- 决策：默认前端直连 Provider；提供可选自建代理解决 Web 端 CORS 与密钥暴露；不做官方云服务
- 理由：隐私、成本、去中心化；本地优先是核心卖点
- 影响：F1-1、F10-2、D5

## ADR-004 · 存储：IndexedDB 先行，SQLite 后补

- 状态：已定
- 决策：`StorageAdapter` 抽象；MVP 全端用 Dexie/IndexedDB；V1 为桌面端增加 SQLite 实现
- 理由：先求"一套代码全平台"，避免双实现拖慢 MVP；资源走独立 AssetStore，迁移只拷目录
- 影响：D4、架构 §7

## ADR-005 · 前端框架

## ADR-017 · 前端框架改用 React 19（**取代 ADR-005**）

- 状态：已定（2026-09-26 追加）。本条取代 ADR-005；ADR-005 原文保留作历史记录，不再作为实现依据
- 决策：前端框架定为 **React 19 + TypeScript + Vite**。配套选型：
  TanStack Router（路由）、Zustand + Dexie liveQuery（UI 状态与数据订阅）、
  `react-hook-form` + `@hookform/resolvers/zod`（表单）、Tailwind CSS v4 + Radix Primitives（样式与无障碍）、
  TanStack Virtual（消息树等长列表虚拟化）、dnd-kit（发言顺序 / 议程排序）、
  react-i18next（i18n）、Vitest + Testing Library（测试）
- 理由：① 本项目 UI 主体是"Zod 驱动的结构化表单 + 长列表 + 拖拽排序"，
  React 生态在这些方向有成熟且互为配套的方案，手写胶水最少；
  ② `packages/schema` 以 Zod 为唯一事实来源，React 侧有与 Zod 直连的表单方案；
  ③ 本地优先、无 SSR/SEO 诉求，Vite + SPA 已足够；
  ④ 代码生成与维护的确定性更高，UI 返工成本在本项目中最高
- 代价：打包体积大于 Svelte（非本项目瓶颈）；需接受 React 生态较快的依赖更新节奏
- 影响：D2、架构 §1 §3、`docs/03` 里程碑决策点、`docs/06` M0 决策点、`README` 技术栈速览
- 备注：ADR-005 原本就写明"若团队更熟 React 可切换"，本次切换正是该条款的落地

## ADR-018 · `.stpack` 的 ZIP 容器自研，并明确确定性策略

- 状态：已定（2026-09-27 追加）
- 决策：
  1. `.stpack` 的 ZIP 容器**自研**，代码放 `packages/packages/src/zip/`，**不引入任何通用 zip 库**；
  2. 只支持 **stored(0) 与 deflate(8)**，无加密、不解压嵌套压缩包；其余一律拒绝并指出具体条目；
  3. 压缩走平台原生 **`CompressionStream('deflate-raw')`**（Node ≥18 与现代浏览器同源；Node 侧可用
     `zlib.deflateRawSync` 兜底），收敛在单个函数里，因此**仍然零依赖**；
  4. **ZIP64 自己实现**，`docs/04` §9 的 ZIP64 要求因此可就地自证；
  5. 载荷 JSON 一律 **canonical JSON**（对象键递归 ASCII 字典序、数组保序、无美化、非 ASCII 不转义），
     即 `docs/04` §11 的 v1-r3 定义；
  6. **"相同内容产生相同字节"只在同一实现内成立**，跨实现一致性以 `entries[].sha256` 为准
     （deflate 的具体实现不同，字节流就不同）
- 理由：
  - `packages/packages` 是适配层，必须同时跑在 Node 与浏览器（Web/PWA 是一等公民），
    所以 Node-only 的 zip 库（yazl / yauzl / archiver）直接出局；
  - `docs/04` §9 对不可信包提出了一整套拒绝要求（zip-slip、符号链接、条目数与体积上限、
    JSON 深度与节点数上限、不解压嵌套包）。通用库这些一条都不提供，仍要自写；
    既然那层必须自己写，容器本身也就只有"窄范围 + 完全可控"才划算 —— **拒绝面比通用库小得多**；
  - 确定性（条目顺序、固定时间戳、键序）由自己掌握，不必依赖第三方库的默认行为；
  - 不新增依赖，体积与供应链风险都不增加
- 代价与缓解：
  - 手写格式解析有风险 —— 缓解是把功能面刻意做窄（两种压缩方法、无加密、无嵌套），
    并把 `docs/04` §12 第 1–7 条逐条写成测试，外加 zip-slip / zip bomb / 伪造 MIME 的拒绝用例；
  - 与"尽量用成熟库"的通用直觉相反 —— 本条的判断依据是**拒绝面**与**跨端**，不是代码量
- 影响：`docs/06` §8.2、`docs/04` §9 §11；`packages/packages` 保持零依赖

## ADR-019 · 流式失败的表达：`error` 携带结构化信息，并定下 `finishReason` 词表

- 状态：已定
- 背景：`StreamEvent` 的 `error` 变体现在是 `{ code: string; message: string; retryable: boolean }`。
  M0-T6 落地时发现 **HTTP 状态码与 `Retry-After` 在这套结构里没有位置**，只能折叠进
  `message` 散文（`HTTP 429: the provider is rate limiting requests (rate limit reached); retry-after 30s`）。
  于是任何要做 i18n、指数退避或"服务商限流中"横幅的调用方，都得去**解析给人看的句子**，
  而 `code` 本来才是稳定词表。
  另外 `done.finishReason` 是自由 `string`：M0-T6 只能自行约定用 `'error'` 表示"流结束于一个
  **已报告过**的失败"，这个约定目前只活在适配器实现里，端口没写。
- 备选：
  1. 只加 `retryAfterMs?: number`，状态码继续留在 `message` 里；
  2. **给 `error` 加结构化的失败细节**：`status?: number`、`retryAfterMs?: number`、
     `providerCode?: string`、`details?: JsonValue`（服务商原始错误体，已脱敏）；
  3. 不动 `error`，另加第七个变体 `type: 'failure'` 承载结构化信息。
- 决策：**选 2**，并同时把 `done.finishReason` 收紧为**开放联合**
  （`'stop' | 'length' | 'tool_calls' | 'content_filter' | 'error' | \`x-${string}\``，与仓库其余
  枚举的"未知值走 `x-` 前缀"约定一致），再把"`error` 之后必有 `done`（`finishReason: 'error'`）"
  写进端口注释。不选 1：状态码是**机器可判**的事实，塞进给人看的句子就永久丢了；
  不选 3：`docs/02` §6 已把事件定为六个变体，加第七个的破坏面更大，而结构化失败本就该由
  `error` 承载。
- 影响面：`packages/core/src/ports/llm.ts`（`StreamEvent`）；`ports/mock/mock-llm.ts` 与
  `packages/providers` 同步；`docs/02` §6 的事件表。
- 验收：M0-T6 的"限流携带 `Retry-After`"用例改为断言**字段**而非字符串；增加一条 mock 用例，
  断言 `error` 之后必定跟 `done{finishReason:'error'}`。

## ADR-020 · Provider 接口形状：拆开 `tokenCounting`、能力可按模型、`listModels` 可取消

- 状态：已定
- 背景：四件在 M0-T6 同时暴露的事：
  1. **`ProviderCapabilities.tokenCounting` 一标志两义。** `ChatRequest.includeUsage` 的注释说
     "only when `capabilities.tokenCounting`"（含义 A：**会上报用量**），而 `LLMProvider.countTokens?`
     的注释说 "absent whenever the provider cannot count without generating, which is legal
     (**the flag in `capabilities` says so**)"（含义 B：**能离线计数**）。两者不是一回事：
     一个只会上报用量的服务商不实现 `countTokens` 是合法的，但按含义 B 写
     `if (capabilities.tokenCounting) await provider.countTokens!(req)` 的调用方**会崩**。
     M0-T6 按含义 A 填标志、故意不实现 `countTokens`，于是这条崩溃路径现在就存在。
  2. **能力是"按 provider"的，现实却是"按模型"。** 同一个 OpenRouter / Ollama 端点下，
     有的模型支持工具调用、有的不支持。任何 provider 级的能力表都只能说"**平均**正确"。
  3. `listModels()` **没有 `AbortSignal`**（`stream` 有），挂住的网关无法由调用方设界。
  4. `ChatRequest.reasoningEffort` 与 `sampling?.reasoningEffort` **重复**，且没写谁优先。
- 备选：
  1. 保持现状，只把 `tokenCounting` 在文档里钉死为含义 A；
  2. **拆标志**：`tokenCounting` 改名 `reportsUsage`，另加可选 `countsTokensOffline`；能力仍为 provider 级；
  3. **拆标志 + 允许按模型覆盖**：`ProviderCapabilities` 作为 provider 级默认值，
     `ModelInfo` 增加可选 `capabilities?: Partial<ProviderCapabilities>`；`listModels(signal?: AbortSignal)`；
     `reasoningEffort` 收敛到 `sampling` 一处。
- 决策：**选 3，但分两步落地**。本 ADR 只定"语义修正"部分（拆标志、`reasoningEffort` 收敛、
  `listModels` 接受信号）；**按模型的能力**只保留字段与优先级规则（`ModelInfo.capabilities`
  覆盖 provider 默认），**M1 接 OpenRouter / Ollama 时再真正填充**。理由：一标志两义会立刻
  伤人（崩溃路径已存在），而按模型的能力在只有 OpenAI 兼容适配器时无人消费 —— 这是本仓库
  "抽象只在出现第二个实现时提取"的直接应用。
- 影响面：`ports/llm.ts`（`ProviderCapabilities`、`ModelInfo`、`LLMProvider.listModels`、
  `ChatRequest`）；`ports/mock/*`；`packages/providers`；`docs/02` §6。
- 验收：新增一条测试断言"标志为 false 时 `countTokens` 可以缺席、且调用方不得依赖它"；
  另一条断言 `ModelInfo.capabilities` 覆盖 provider 默认值的优先级。

## ADR-021 · `vision` 标志永远为假：删掉它，多模态到来时再用 `assetId` 引用图片

- 状态：已定（**分期**：本轮只删标志；多模态内容延后，方向见「决策」）
- 背景：`ProviderCapabilities.vision: boolean` 与 `ModelInfo.vision?: boolean` 都已存在，
  但 `ChatMessage.content` 的类型是 `string`。因此**没有任何适配器能把图片发给模型**，
  `vision` 只能恒为 `false`：一个永远为假的能力标志比没有它更糟，因为它会让 UI 以为
  "这条路以后能通"，而按本仓库的约定，**"以后可能用得上"的抽象不该先写**。
- 备选：
  1. **删掉两处 `vision` 标志**，等真正做多模态时再加；
  2. 把 `ChatMessage.content` 放宽为 `string | ContentPart[]`，`ContentPart` 为
     `{ type: 'text'; text } | { type: 'image'; assetId; mime }`（**用 `assetId` 而非 base64**）；
  3. `content` 保持 `string`，另加 `attachments?: AssetRef[]` 到消息（端口与实体都加）。
- 决策：**选 1（现在）**，并把 **2 的方向预先记下**（图片以 `assetId` 引用、绝不 base64 内联），
  这样 M1 做多模态时不必重新争论。理由：选 1 的改动面只有端口的两行，且符合"不写用不上的抽象"；
  选 2/3 都要动**实体契约**（进而动 `docs/04` 的载荷与 JSON Schema 产物），而当前**没有任何
  消费方**——为尚不存在的功能改数据契约，正是本项目"数据契约先于界面"要避免的反面。
- 影响面：仅删标志时只碰 `ports/llm.ts` 与 `packages/providers` 的能力表；
  若日后选 2/3，则需同步 `packages/schema` 的消息实体、`docs/04` 载荷与
  `schema/package-1.json`（有逐字节漂移测试），**那时应当单独一个小版本提交**。

## ADR-022 · 行寻址：`settings` / `migrations` 没有 `id`，而注释承诺的 `getBy` 并不存在

- 状态：已定
- 背景：`ports/storage.ts` 的 `RowBase` 注释写着："§7 的集合不都是主键即 `id`（`settings` 用
  `key`），但除了 `settings` 每个都有 `id`，**因此本端口通过 `getBy` 处理它**。" 两处都不成立：
  1. `Collection<T>` 上**没有 `getBy`**（只有 `get(id)` / `list` / `put` / `putMany` / …）；
  2. `docs/02` §7 的 `migrations` 是 `(version, appliedAt)`，**同样没有 `id`** —— 注释漏了它。
  后果：M0-T7 落 Dexie 时只能把这两个集合的行都塞在 `id` 下（`settings` 行的 `id` 实际存放配置键），
  即**对 §7 的实质偏离，且没有任何文档记录它**。
- 备选：
  1. 给 `Collection<T>` 加 `getBy(index, value)`，并让 `settings` / `migrations` 的行类型**不含 `id`**；
  2. 给端口引入**每集合的主键声明**（`PRIMARY_KEYS[name]`），`get` 的语义随之改变；
  3. 改 `docs/02` §7：让这两张表的**主键列就写 `id`**（值分别为配置键与版本号），端口不动。
- 决策：**选 3**，并同时**删掉 `RowBase` 注释里 `getBy` 的说法**。理由：`settings` / `migrations`
  是**本地库内部**的表，从不进入 `.stpack`、也不参与实体契约；为两个内部表给整个端口加一层
  泛化的主键机制（选 1/2）是"为局部需求改造全局抽象"，而选 3 只需改 §7 的措辞。若将来 SQLite
  后端确实需要复合主键，再单独决策。
  另外建议在 §7 明确写一句：**`settings.id` 存配置键、`migrations.id` 存版本号** —— 免得下一个人
  再猜，也免得偏离再次发生而无人记录。
- 影响面：`docs/02` §7 的表格与说明；`ports/storage.ts` 的 `RowBase` 注释。`packages/storage`
  已按此实现，**无需改动**；但应补一条断言"`settings` 行以 `id` 存放配置键"，把这个约定钉住。

## ADR-023 · `Query.field` 省略时的语义：报错，而不是默默回退

- 状态：已定
- 背景：`Query.field` 的注释解释了它为什么必须显式 —— "a bound without a field is ambiguous:
  §7 has collections whose first indexed field is not the range one（`messages` 是
  `(sessionId, parentId)`，但它有用的范围是 `createdAt`）" —— **然而它本身是可选的**。
  M0-T5 的 mock 于是把省略时的 `field` 默默回退成"第一个 `where` 键"，导致
  `{where:{createdAt:10}, from:1, to:5}` **静默返回空数组**（把 `from`/`to` 应用到了一个恰好
  等于 10 的字段上）。M0-T7 为了让适配器与替身不产生分歧，**照抄了这个回退**，并用一句具名
  测试把它钉住 —— 也就是说，一个静默的错误答案现在被测试**固化**了。
- 备选：
  1. 保持现状（回退到第一个 `where` 键），只把行为写进文档；
  2. **有 `from`/`to` 而 `field` 缺席时抛错**，mock 与适配器一起改；
  3. 让 `field` 在有 `from`/`to` 时**类型必填**（联合类型表达）。
- 决策：**选 2**。它把静默的错答案变成一次立刻可见的失败，改动只涉及端口的两个实现与一条
  mock 测试；选 3 在类型上更"安全"，但本项目的查询类型已混用 `Partial<Record<…>>`，
  再叠一层联合会明显拖累可读性，而收益与 2 相同。选 1 不可取：**一个被测试固化的错误语义，
  日后会变成"兼容性承诺"**。
- 影响面：`ports/storage.ts` 的 `Query` 注释；`ports/mock/mock-storage.ts` 及其测试；
  `packages/storage/src/indexeddb/adapter.ts`（把回退换成校验）。`docs/02` §7 不需要改。
- 验收：把 M0-T7 那句具名测试从"断言静默回退"改为"断言抛错"，并在 mock 侧加同一条。

## ADR-024 · 查询边界的可比性：只接受 `number` / `string`，其余抛错

- 状态：已定
- 背景：ADR-023 禁掉了"缺 `field` 就猜"这一类静默错误答案，但没有覆盖同类：
  `compareValues`（mock 与 Dexie 适配器各一份）对**非 number / 非 string** 的值一律返回 `0`
  ——也就是"相等"。于是一个装着 `Date`（或数组、对象）的 `from` / `to` 会让**所有行都落在
  范围内**：静默返回全表，而不是报错。两侧都没有测试钉住它。M0-T7 复查时发现。
  另外 `Query.field` 的类型是 `keyof TRow & string`，而实现为了拿到通用行类型常把
  `Query<T>` 转型为 `Query<RowBase>`，于是 `field` 在实现里退化成只剩 `'id'`：真实的范围字段
  只活在调用方的泛型里，类型对实现零帮助（不致命，但一次"顺手修正"就可能变成真 bug）。
- 备选：
  1. 不动，只在文档里说明边界只支持 `number` / `string`；
  2. **比较前校验**：`from` / `to` 不是 `number | string` 就抛 `StorageQueryError`；同时把
     `Query.from` / `Query.to` 的类型从 `unknown` 收窄为 `number | string`；
  3. 支持 `Date`：先归一化成毫秒数再比较。
- 决策：**选 2**。`docs/02` §7 的第一条约定就是"时间戳为毫秒"，因此 `Date` 是
  **调用方的错误用法**，不是缺失的能力 —— 选 3 等于为一个不该出现的类型增加分支；选 1 则又
  把静默错答留在原地，与 ADR-023 刚立的原则相悖。顺带在 `Query.field` 的注释里写明：实现可以
  转型，但**必须**按调用方给的字符串取值，不得假定只有 `id`。
- 影响面：`ports/storage.ts`（`Query` 的边界类型与注释）、`ports/mock/mock-storage.ts`、
  `packages/storage/src/indexeddb/adapter.ts` 及两侧测试。`docs/02` §7 无需改动（依据已在）。
- 验收：mock 与适配器各加一条测试 —— `from: new Date(0)` **抛错**而非返回全表；类型收窄后
  调用方在 `tsc` 阶段就会拒绝 `Date`。

## ADR-025 · 桌面端的 HTTP 通道：自建 `llm_stream` 字节管道，不用 `tauri-plugin-http`

- 状态：已定
- 背景：ADR-003 定「默认前端直连 Provider，可选自建代理解决 Web 端 CORS 与密钥暴露」，
  HANDOFF §9 第 9 条要求**桌面端由 Rust 侧直连**以绕开 CORS。Tauri 2 至少有两条现成路。
- 备选：
  1. 官方 `tauri-plugin-http`（把 `fetch` 搬到 Rust）+ `http:default` 权限；
  2. **自建 command**：`llm_stream(request, on_event: Channel<…>)` + `llm_cancel(requestId)`，
     Rust 只搬字节，SSE 解析 / 错误分类 / 脱敏全部留在 JS；
  3. 什么都不做，桌面端也用平台 `fetch`（等于把 CORS 交给服务商决定）。
- 决策：**选 2**。
  - 选 1 的 ACL 是**按域名白名单**授权的，而 BYO-Key 的 base URL 是用户当场填的：要么把白名单
    放到近乎全开（等于没有白名单，却仍留着「看起来被限制住了」的错觉），要么每次改配置都要动
    能力文件。这与 ADR-003「用户自带端点」的模型直接冲突。
  - 选 2 把**拒绝面**重新握在自己手里：Rust 只做四件事 —— 校验 scheme 只允许 `http`/`https`、
    发请求、把原始字节分块推给 JS、响应取消（不取消就等于让用户为已经不要的生成继续付费）。
  - 关键分工：**Rust 不解析 SSE**。`packages/providers` 里那个零依赖 SSE 解析器与四种错误映射
    已经有测试，在 Rust 里再写一份就是制造第二个真相源。所以 Rust 连 UTF-8 都不解码，
    **以 base64 传原始字节** —— 一个 SSE 帧可能在多字节字符中间被切开，按块解码就会损坏内容。
    代价是 33% 的传输膨胀，换来的是「JS 侧永远是同一份字节语义」。
  - 选 3 不可取：HANDOFF §9 第 9 条与 ADR-003 都已写明桌面端要绕开 CORS。
- 影响面：`apps/desktop/src-tauri/src/`（新）；`apps/desktop/src/transport/tauri-fetch.ts`（新），
  它把 channel 事件还原成一个**真的 `Response`**；`apps/web` 只多一个可注入传输的挂载参数
  （`mountApp(root, { transport })`，默认平台 `fetch`）。`packages/providers` 的 `FetchLike`
  注释早就预告了这条通道，**端口与适配器一行都不用改**。
- 验收：跨语言契约用**同一份夹具**钉住
  （`apps/desktop/src/transport/fixtures/llm-stream-events.json`）：Rust 侧断言事件枚举序列化成
  夹具里的 JSON，TS 侧把同一份帧喂给假的 channel，断言还原出的 `Response` 的状态码、响应头与
  正文字节一致。**任一侧改形状，另一侧的测试就会红**。另有 Rust 侧对本地 HTTP 服务器的端到端
  用例（正常流 + 取消）。

## ADR-026 · Rust 侧 HTTP 客户端用 `reqwest` + `rustls`，不依赖系统 TLS 栈

- 状态：已定
- 背景：`reqwest` 在 Windows 上默认走 `native-tls` → schannel，即复用系统证书库。
  两个考虑：跨平台行为是否一致；以及这条代码路径在开发机上还能不能被真的跑通。
- 备选：
  1. `native-tls`：产物体积更小、复用系统信任库（企业自签证书友好）；
  2. **`rustls-tls`**：自带根证书集（`webpki-roots`），所有平台行为一致。
- 决策：**选 2**。桌面端要连的是用户自己填的公开 HTTPS 端点，**行为在所有平台一致**比复用系统库
  更值钱；而且这是唯一能让这条路径在开发机上被端到端测到的选择（本机的 schannel 全线不可用，
  见 `LOCAL-DEV-NOTES.md`）。代价与缓解：`rustls` 会带进 `ring` 一类的 C 依赖，首次构建更慢、
  产物体积略大；企业自签/内网证书的场景**不受影响** —— 那种场景本来就该用本地网关或代理，
  而不是靠系统信任库把证书校验蒙过去。
- 影响面：仅 `apps/desktop/src-tauri/Cargo.toml`。Web 端不受影响（用浏览器自己的 TLS）。

## ADR-027 · BYO-Key 凭据的落点：本地 `settings` 集合，永不进入包、日志与消息元数据

- 状态：已定（M0 的口径；桌面端系统 keyring 记为 M1 方向）
- 背景：HANDOFF §4.1 不变量 6 要求「密钥绝不进入包、日志与消息元数据」，但没写**它该存在哪**。

- 备选：
  1. **存本地 `settings` 集合**（行 `id: 'llm.provider'`），随本地库走；
  2. 只存内存（每次重开都要重填，「重启后数据仍在」在配置层面直接失效）；
  3. 桌面端存系统 keyring（Tauri 插件 / `keyring` crate），Web 端退化为选 1。

## ADR-028 · 响应式读取的接缝：实现层暴露 Dexie 实例，端口不增长

- 状态：已定
- 背景：ADR-017 把 Dexie `liveQuery` 定为响应式读取机制。M0-T8 **实测**（不是推测）三件事：
  1. `liveQuery` 的 querier 运行在**只读** Dexie 事务里，而端口唯一的入口
     `StorageAdapter.transaction()` 固定开 `rw`（覆盖所有表），于是 querier 里调它会抛
     `ReadOnlyError: Readwrite transaction in liveQuery context`，订阅**一次值都不发**
     —— 浏览器里就是聊天记录悄悄不再更新，正是 ADR-023 / ADR-024 要消灭的那类静默错答；
  2. `Dexie.liveQuery` 是模块级 API（靠全局 `storagemutated` 事件），**无法**绑定到某个私有实例；
  3. `createIndexedDbStorage()` 只返回端口的四个成员，UI 拿不到那个实例。
- 备选：
  1. UI 自己再开一个同名 `Dexie` —— 两个实例抢同一个 schema 版本，不可行；
  2. UI 自写一套读写适配器（复制 `packages/storage` 的写入路径）—— 得到第二份无人测试的真相源；
  3. **实现层暴露实例**：`IndexedDbStorage extends StorageAdapter { readonly db: Dexie }`，
     并约定 `db` 只做响应式**读**、写一律走 `transaction()`；
  4. 给端口加响应式订阅方法（`observe(collection, query, cb)`），把 Dexie 关在包里。
- 决策：**选 3**。选 1 不可行；选 2 正是"数据契约先于界面"要避免的重复实现；选 4 分层更漂亮，
  但它把**某一个后端的 reactivity 机制**提升成端口概念 —— 端口一共四个成员，为一种后端加第五个
  成员是"为局部需求改造全局抽象"（与 ADR-022 同构的取舍）。选 3 的代价是 UI 能看见 Dexie，
  所以用**注释里的硬规则**（写路径只有一条）加**两条测试**把它夹住。若将来 SQLite 后端也需要
  响应式读取，再回头评估选 4。
- 影响面：`packages/storage/src/indexeddb/adapter.ts`（新增 `IndexedDbStorage` 接口）、
  新增 `packages/storage/src/indexeddb/live-query.test.ts`；**`packages/core` 的端口一行未改**。
- 验收：两条具名测试 —— ① querier 里调 `transaction()` 必定报只读错（把失败模式钉住：
  Dexie 哪天放开这条限制，测试就会红，届时可以正式撤掉接缝）；② 经适配器写入的行，
  会被挂在 `db` 上的 `liveQuery` 订阅观察到。

# M1 开工（ADR-029）

## ADR-029 · Prompt 块与预设的契约归属：进 `packages/schema`，不做 core 的私有类型

- 状态：已定（实体已落地：`packages/schema/src/entities/prompt.ts`；PromptComposer 本体随 M1-G4）
- 背景：M1-G4 要实现 PromptComposer，而 `docs/02` §5.1 只给了 `PromptBlock` 的**接口草案**
  （`role` / `content` / `position` / `depth` / `order` / `budget` / `conditions`）。这块形状有两种
  放法，判断依据是三条**既有事实**，不是偏好：
  1. `data/promptPresets.json` **已经是 `.stpack` 的载荷之一** —— `docs/06` §8.4 记着
     「M0-T3 的 `validate` 跳过 `data/promptPresets.json`」，也就是说这个名字早在冻结格式的清单里，
     只是**还没有 schema 去校验它**；
  2. `Session.refs.promptPreset` 是**必需**引用（ADR-010 要求引用必须钉住版本），M0-T8 只能用内置
     占位 id 顶上，因为没有实体可指；
  3. ADR-016：跨模块的结构一律来自 `packages/schema`。
- 备选：
  1. **各定义一份**：core 里放运行时类型，M1 稍后再在 schema 里补实体 —— 两处形状必然漂移，
     正是本项目最忌讳的那类问题（对照 ADR-028 与 UUIDv7 收敛）；
  2. **只在 schema 定义、core 消费**：`PromptBlockSchema` / `PromptPresetSchema` 进
     `packages/schema/src/entities/prompt.ts`；`PromptComposer` 保持纯函数，输入是
     `PromptPreset` + 一个 `PromptContext`；
  3. 先用 `unknown` / 全开放字段顶着 —— 与「数据契约先于界面」直接冲突。
- 决策倾向：**选 2**，并把 §5.1 的草案**逐字**落成 Zod（`budget.share`、`budget.priority`、
  `conditions.keywords` / `minTurns` / `timeOfDay` 都保留）。`position` 与 `priority` 是**闭合**枚举：
  装配顺序与裁剪逻辑要对它们做穷尽 `switch`，开放它们只会让裁剪出现"没写到的分支"。
- 落地时查清的两件事（都比草案里假设的更省事，也各有一条要记住的结论）：
  1. **不动任何已发布的 JSON Schema 产物。** `packages/schema/src/json-schema.ts` 只导出 manifest 与
     tools 两份 schema，**实体不在其中**；实测 `pnpm schema:export` 重写两份产物后 `git diff schema/`
     为空。`docs/04` 的载荷清单也不用改：`promptPresets` 本来就在它的**固定枚举**里
     （`schemaVersions` 的键、`contents.counts` 的键、`prompt-preset` 包类型都已列出）。
  2. **预设是扁平实体，不是 head+version 两集合。** `docs/04` §2 的载荷写作 `PromptPreset[]`
     （而 worlds 明确写作 `WorldVersion[]`），`docs/02` §7 的行也直接带 `blocks[]` 与 `version`。
     因此 **ADR-010 的「不可变版本」对预设不适用**，而历史可复现由
     `MessageMeta.promptSnapshotId`（每条消息存下它当时用的装配）保证 —— 预设更像一份**设置**：
     用户会一直调，`version` 只是显示与迁移用的计数器。`docs/02` §7 已补一句说明，免得下一个人
     把那当成"漏了版本集合"。
- 影响面：`packages/schema`（新实体 + 导出 + JSON Schema 产物）、`packages/core/src/engine/prompt/`
  （M1-G4）、`apps/web/src/chat/prompt.ts`（M0-T8 的内置装配将被真正的 composer 取代）、
  `docs/06` §8.4 的"跳过校验"说明。
- 验收：M1-G4 的快照测试覆盖**装配顺序**与**超预算裁剪**（`docs/06` §2.1 的验收原文）；
  `schema/package-1.json` 与 Zod 定义一致（既有漂移测试）。

# M1-G1 落地（ADR-030）

## ADR-030 · i18n 的边界：什么算"文案"、语言从哪来、哪一层可以 import 它

- 状态：已定
- 背景：M1-G1（`packages/i18n` + 全界面转换 + 禁止裸字符串的 lint 规则）在落地时冒出一批
  "两种做法都讲得通"的边界问题。它们都不难，但**判错会以很隐蔽的方式伤到用户**——比如英文界面的
  用户开始向模型发英文提示词，或者用户刚点的语言被一次迟到的读取改回去。这一节把六条边界一并定下。
- 决策：
  1. **界面文案 ≠ 模型提示词。** `apps/web/src/chat/prompt.ts` 里的中文是**送给模型的系统提示词**，
     它**不随界面语言变化**：语言偏好是显示，而它决定模型看到什么、从而决定模型怎么回话 ——
     让英文界面顺带把提示词也换成英文，是**行为变更**，不是本地化。规则把该文件列为**精确到文件**的
     临时豁免，并在注释里写明失效条件：M1-G4 把这段文字变成 `PromptPreset` 的**块数据**（ADR-029）后
     删除豁免。豁免必须带**反蔓延测试**（同目录的兄弟文件仍会被报）—— 一个能自己长大的豁免名单，
     就是规则死亡的方式。
  2. **开发日志用英文，不进目录。** `console.error` 之类是给开发者看的，而本仓库面向开发者的散文
     一直是英文。给它们建 key 会让目录里混进永远不会显示给用户的句子，日后没人敢删。
  3. **语言偏好：`settings` 行 → `navigator.languages` → `zh-CN`**（首次运行**跟随浏览器**，
     而不是硬编码中文：选择器是偏好，不是唯一能读懂界面的途径）。切换是**乐观**的——先改状态再写库，
     写失败只记录错误的**名字**并把选择留在屏幕上（用户按了就是要它，把界面回滚是第二次意外变更）。
     选择器里的语言名**用各自的语言**（`中文` / `English`）：读它的人可能读不懂当前界面语言。
  4. **React 绑定留在 `apps/web`，`packages/i18n` 保持零依赖零框架。** 目录是数据、`t` 是纯函数；
     hook、store 与持久化属于应用层。这样 CLI、桌面壳、测试都能直接读目录而不拖进 UI 运行时，
     也维持了本仓库对 `packages/*` 的既有约定。
  5. **测试必须钉住自己的语言。** jsdom 报 `navigator.languages` 是 `en-US`，而首屏按第 3 条跟随浏览器，
     于是所有断言中文的旧用例会跑在英文界面上。**断言文案的测试必须显式声明它断言的是哪种语言**，
     而不是把断言放松成"包含任意语言"——后者会让测试在两种语言下都通过，也就等于没测。
  6. **lint 规则只说它真正管的事。** 规则抓两件：`apps/*/src` 里的 CJK 字符，以及 `title` /
     `placeholder` / `aria-label` / `aria-description` / `alt` 这些**用户可见属性**上的裸字面量
     （拉丁文同样要 `t(...)`——`title="Settings"` 和 `title="设置"` 一样没本地化）。
     **它抓不到的**：JSX 文本节点里的拉丁文散文、以及 `className`/`id`/`role`/`data-*` 这类合法持有
     裸字符串的属性 —— 这一条**写在规则自己的注释与 `CONTRIBUTING.md` 里**。有盲区没关系，
     声称得比实际多才有关系。
- 附带一条**应用内部的分层规则**（由一次真实的循环导入换来）：`apps/web/src/db/**` 与 `chat/**`
  这类下层模块**不得 import i18n/state 层**。M1-G1 落地时 `db/repository.ts` 为了给新会话填默认标题
  import 了 `translate`，于是形成 `repository → use-translation → locale-store → repository` 的环，
  运行时报 `translate is not a function`（绑定尚未初始化）。修法是**分层**而不是护栏：默认标题属于
  **持久化数据**，由调用方决定并传入；`chat/providers.ts` 用它在同一文件里已经写好的
  `{ key, params }` 形式把句子留给渲染处翻译。**循环导入是"层被画错了"在没有编译器时的证据。**
- 影响面：`packages/i18n`（新包）、`apps/web/src/{i18n,state/locale-store.ts}`、
  `apps/web/src/db/repository.ts` 与 `chat/providers.ts`（去掉 i18n 依赖）、
  `tools/scripts/check-i18n-literals.mjs`、`CONTRIBUTING.md` §5.3。
- 验收：检查器 0 违规（`pnpm lint` 因此变绿）；「切换语言全界面生效」由真实 DOM 测试覆盖
  （切换后同一个视图渲染另一种语言）；持久化回读 + 损坏值回退 + 未识别错误码落到通用文案各有测试。

# M1-S6 前置（ADR-031）

## ADR-031 · 变量系统的契约：`SessionState.vars` 就是它

- 状态：已定
- 背景：M1-S6（状态栏最小版：自由变量展示与编辑）记在 `docs/06` §10.3 时，我写的是"数据契约至今
  不存在"。**那句话不准确**：`packages/schema` 的 `SessionStateSchema` 已经把大部分契约冻结了，
  只是没有任何一处**把它当作变量契约说出来** —— 于是"变量挂在哪、能不能存对象、跟存档什么关系"
  这些问题的答案躺在一个注释里，而提问题的人不会去读它。这条 ADR 补上那句话，并定下 schema 没说的。
- **schema 已经冻结的部分**（不是新决定，是把它讲明白）：
  1. **作用域**：变量在**会话**上（`vars`），是一张扁平表 —— 不是"会话 → 角色 → 世界"的运行时
     查找链。世界与角色提供的是**初始值**，在会话创建时种进 `vars`（M1-S1），此后只有一个真相源。
     因此 `{{getvar::hp}}` 不需要前缀语法，也不需要优先级规则。
  2. **值的形状**：只允许**原始值**（`string | number | boolean`）。对象与数组会立刻牵出
     "改了哪个字段"的补丁语义，那是 M1-W2 的地盘；状态栏编辑的也是原始值。规则包需要的复杂结构
     走 `sheets` —— 那里 `unknown` 是**刻意**的，因为 schema 归规则包所有，core 不该知道。
  3. **持久化与回滚**：变量属于**一份** `SessionState` 快照，而 checkpoint 整份快照它
     （`docs/04` §6 的原文：`scene`、两个时钟、自由变量、规则包表、截止时间）。所以 M1-S6 的
     「变量随存档保存与恢复」与 M1-T4 的时钟回滚、M1-M1 的定点存档是**同一次写入**，
     不是三条各自回滚的线。
- **本次决定的三件事**（schema 没说）：
  1. **`setvar` 是赋值，增量另起一个宏名。** `{{setvar::hp::10}}` 赋 10；
     **`{{addvar::hp::-3}}`** 做数值增量。**不接受** `{{setvar::hp::+3}}` 这类"看起来像增量"的写法：
     它与字面量字符串 `"+3"` **无法区分**，同一条预设会在两个版本里变成两种行为 ——
     **宏文本必须一眼看出是赋值还是增量**。`addvar` 的目标不是数字时**原样保留并上报**。
  2. **M1 里只有人能改变量。** 状态栏直接写 `vars`；`docs/02` §5.5 的 `update_state` /
     `update_relation` 工具是**将来**的 AI 通道（工具执行属于 M2+），现在不实现。但"将来会有机器写入"
     这一事实现在就决定了形状：写入必须经过**纯函数**（旧状态 + 变更 → 新状态），不得就地改对象 ——
     ADR-010 的不可变，以及将来"AI 的改动可否决"，都靠这一点。
  3. **未定义变量的读：原样保留并上报，不替换成空串。** 与 M1-G4 的宏规则完全一致
     （进 `unresolvedMacros`）：静默变空会删掉半句话而没有人发现。
- 一处实现细节（因为原始值要被替换进文本）：`getvar` 取到数字/布尔时按**稳定文本**转换
  （布尔写 `true` / `false`；数字用 `String()` —— 对游戏计数器会遇到的每个取值都是十进制，
  只有在 1e21 以上或 1e-6 以下才会转成科学计数法，而那时是**数据**出了问题，不是宏的问题）。
  这段转换**已经在 `readVariable` 里**（`String(value)`），不是待办事项；它**不进目录**：那是数据，不是文案。
- 仍然延后：变量上下限与夹取（规则包与状态栏的事）、按 actor 的变量（`sheets` 已留位置）、
  AI 写变量的提案流（将来复用 M1-W2 的采纳/否决）。
- 影响面：`packages/core/src/engine/prompt/macros.ts`（**已落地**：`setvar` 赋值、新增 `addvar`）、
  `apps/web` 的状态栏（M1-S6）、`apps/web/src/chat/clock.ts` 的 `variables` 入参
  （从空对象改为 `SessionState.vars`）。
- 验收：`setvar` / `addvar` / `getvar` 各有用例；未定义变量原样保留且出现在 `unresolvedMacros`；
  变量写入是纯函数（旧状态不变、返回新状态）。

# M1-M1 / M1-T4 / M1-S6 前置（ADR-032）

## ADR-032 · 实时会话状态住在会话行里（`Session.state`），不是第 19 个集合

- 状态：已定
- 背景：`SessionState`（场景、两个时钟、自由变量、规则包表、截止时间）在 schema 里**定义完备** ✓，
  也被 checkpoint 整份快照 ✓ —— 但它**没有持久化落点** ✗：既不是 `Session` 的字段，也没有对应集合。
  后果已经在三处显形：`chat/clock.ts` 只能读 `Session.initialClock`（唯一被持久化的时钟）；
  包导入导出把 `state.json` 从"最新检查点"**推导**；而**没有检查点的包根本无法持久化时钟**，
  导入器只能发警告。三个 M1 任务（定点存档、时钟入存档、变量随存档）都卡在这一点上。
- 决策：**`Session.state: SessionState`**，理由三条：
  1. **它本来就是文档里的形状。** `docs/02` §7 的接口草图里写着 `state: SessionState` ✓；
     而 ADR-022 把集合清单冻结成"§7 的**十八个**集合，**逐字**" ✓ —— 新开一个 `sessionStates`
     集合等于改写一份被逐字冻结的清单 ✗，而这一条本来不需要改。
  2. **实时状态与它所属的会话一起读写。** 会话行本来就每回合被写（`headMessageId`）✓，
     多带一份状态**不引入新的写竞争** ✓，读会话即得状态 ✓。
  3. **检查点仍是独立集合里的一份完整快照** ✓（`docs/04` §6 的载荷不变）。实时状态是"现在"，
     检查点是"某个时刻" —— **两者都存在，才有"读档回滚"可言** ✓。把实时状态做成"最新检查点"的
     投影（导入器目前的权宜之计）在本机是错的：手动打点之间的时间就无处安放 ✓。
- 仍然留给实现的两件事（不是本 ADR 的范围）：快照写回时的**顺序与冲突**（状态、议程状态、卡司状态
  是跨集合写，见 `ports/storage.ts` 关于多集合事务的说明），以及 `Session.updatedAt` 是否随状态更新。
- 影响面：`packages/schema`（`SessionSchema` 增字段 + 漂移测试）、`apps/web/src/db/repository.ts`
  （读写该字段）、`apps/web/src/chat/clock.ts`（`clockOf` 由 `Session.initialClock` 改为 `state.clock`
  —— 读取早已收在**一处**，所以这是改一个函数）、`packages/importers`（`state.json` 改为导出
  `Session.state`，不再从最新检查点推导）。
- **`Session.state` 是必填，旧行在读取处补默认值**（补记，因为它决定实现怎么下手）：
  一个**没有** `state` 的会话是不可用的（时钟、场景、变量全无 ✓），所以 schema 里它是必需字段 ✓；
  而**在它存在之前写下的行**（M0/M1 早期版本创建的 ✓）要在**读取边界**上被补成一个由 `initialClock`
  推出的默认状态 ✓ —— 读取处本来就是"把不可信的行变成可信值"的地方，与 `readLocaleSetting` 对
  损坏值回退是同一条规则 ✓。这样**不需要**为 M1 动 `migrations` 集合：迁移是给**含义**变化用的，
  而这里缺失字段的含义可以由既有字段**推导**出来 ✓。下一次写入自然把它落成真实的行 ✓。
- 验收：刷新后时钟与变量仍在（DOM 测试）；会话行的 `state` 读写 round-trip；包的 `state.json`
  等于导出那一刻的 `Session.state`。

# 分享面 / M1-G3 复数半边 前置（ADR-033 / ADR-034）

## ADR-033 · 主题包是"一批值"，不是一层覆盖

- 状态：已定
- 背景：`docs/04` §12-16 要求 `kind: "theme"` 的包（`data/theme.json` + `assets/*`），而 M1-M3 只做了
  世界 / 角色 / 会话三类，`docs/06` §10.5 记着它**没有归属**。M1-G2 之后应用**已经有**主题，所以问题
  不再是"要不要"，而是"**一个主题包能改什么**"。
- 决策：**应用主题 = 写入用户自己的外观设置行**（`theme` / `fontScale` / `messageWidth`，M1-G2 已有的
  三行），**不新增第四个存放显示状态的地方**。理由三条：
  1. **只有一个实时的真相**：覆盖层意味着"这个颜色到底是什么"有两个答案 —— 而 ADR-030 已经裁决过
     两样东西争夺同一个显示决定会发生什么。
  2. **用户能走得掉**：应用之后改字号就只是改一个设置；有覆盖层则每次改动都要先问"这是主题还是我"，
     而唯一的出口是一个必须记住"原来是什么"的取消操作。
  3. **它让包保持诚实**：调色板 + 排版默认值是**数据**；覆盖层必须携带**行为**（何时赢、何时让），
     而可分享文件里的行为就是**换了名字的脚本**。
- **可设置面是量出来的**：`app.css` 恰好声明 **11 个调色板 token**（`--bg` `--surface` `--text`
  `--muted` `--line` `--accent` `--accent-text` `--ok-bg` `--ok-text` `--danger-bg` `--danger-text`）。
  主题只能设这些；**未知属性名在导入时带 finding 拒绝** —— 在共享产物里它要么是作者的拼写错误
  （**只有告诉他，他才能改**），要么是版本不匹配，而导入器不能吞掉。
- **`--font-scale` / `--message-width` 不在那个列表里，而这个差别本身就是契约**：它们从不在 `app.css`
  里声明，而由 JS 从用户自己的设置行写入。所以主题里的 `fontScale` / `messageWidth` 是**对用户那几行的
  提议**，不是调色板 token —— 这正是"应用主题写用户的行"的**机械**理由。
- **"缺席"不等于"默认值"**：字段缺席＝对该项不表态、保留用户当前值；这与"该主题要求 1.0"是两件事。
  越界值在导入时**带 finding 拒绝**而不是静默夹取：夹取会把作者的错误从**能修它的人**眼前藏起来。
- 刻意不决定：非视觉资源（声音 / 图标）、主题是否与会话绑定（**不该**绑定 —— 它是显示偏好，写明比
  暗示好）、内置默认主题（它必须无 JS、无存储也能工作，因此留在 `app.css`，不是包）。
- 验收：§12-16 通过；应用主题写入三行且界面立刻改变；带越界值的包被拒绝并给出 finding；
  `contents.counts.themes` 等于真实条数。

## ADR-034 · 多个 Provider = N 行 `settings`（键 `provider.<uuid>`），不新开集合

- 状态：已定
- 背景：M1-G3 的行写着"增删 Provider"（**复数**），而 `settings` 只有一行 `provider`，会话又通过
  `refs.modelConfig` 钉住配置 —— 于是 **id 空间必须先于界面存在**（`docs/02` §7 曾记为待定契约）。
- 决策：
  1. **不造第 19 个集合**：ADR-022 把集合清单冻成"§7 的**十八个**、**逐字**"，而 `settings` 本来就是
     `(key, value)` 表 → "几份配置"就是几行，机制已经存在。
  2. **"用哪一个"会话已经回答了**：`refs.modelConfig` 本身就是那个 pin，所以游玩时**不需要**任何
     "当前 provider"全局；只剩"新会话该钉哪个"，由一个 `provider.default` 键回答 —— 那是**默认值事实**，
     不是关于运行中会话的第二份真相。
  3. **旧行由读取方收养**：M0/M1 写的那行 `provider` 在首次读取列表时成为第一行 `provider.<id>`；
     与 `completeState`（ADR-032）同一条规则 —— **读取处才是把旧行变成可信值的地方**，而迁移是给
     **含义**变化用的。
- **两条是量出来的，不是假定的**：`IdSchema` 是 `string().min(1).max(200)`，**没有字符集约束**，所以
  `provider.<uuid>` 是合法的行 id；`Session.refs.modelConfig` 是 `{ provider: string, model, params, … }`
  —— 一个**裸字符串**，不是带版本的 `Ref`，也不是 `UuidV7` → **行键就是那个 pin**，不需要另设 id 字段。
- 由此推出一条**承重规则**：因为 pin 没有版本，会话跟随配置**此刻的内容** → 改一份配置会影响所有钉住
  它的会话，而**删除是唯一能断开链接的手段** → **被引用的 provider 不能删**（拒绝时点名是哪些会话在钉
  它）。软删除会让每个读取方永远过滤，而"照删不误"会留下悬空引用 —— 那正是 `docs/04` §12 在别处已经
  定义为缺陷的东西。也正因如此**不引入版本 pin**：需要冻结凭据的会话，本来就是**另一份配置**。
- 其余：**密钥是每行一份**（G3 的信封自描述且住在单行里，加密部分一字不改）；模型列表与连接测试都是
  **每个 provider** 的（它们是端点的属性，不是"应用的"属性）。
- 刻意不决定：候选链 / 失败转移、按会话覆盖密钥、加密迁移（G3 已落地）。
- 验收：新增 / 编辑只影响那一行；被引用时删除被拒、无引用时可删；旧 `provider` 行首次读取即被收养；
  模型列表与连接测试针对被编辑的那一行；**另一个** provider 的密钥绝不出现在该 provider 的错误文本、
  日志或导出包里（把 G3 的四条反证扩到"两行"情形）。

# 扮演与调度（ADR-035）

## ADR-035 · 实时卡司状态住 `Session.state.cast`；存档里的 `castState` 是"当时"

- 状态：已定
- 背景：M1-S5 的调度器要读"**此刻**谁在场、谁被禁言"，而 schema 里只有 `SessionRefs.cast`（**钉住的名册**）
  与 `Checkpoint.castState`（**某个存档点的快照**）—— 前者是"这一局有谁"，后者是"那时谁在场"，都不是
  "现在"。于是 M1-S4 需要给**实时**卡司状态一个归宿。
- 决策：住在 `SessionState.cast`，即 ADR-032 给实时状态的那个家（会话行的 `Session.state`）；形状为
  `z.record(IdSchema, CastStateSchema)` 且**可选**（缺席＝按默认在场），纳入 `defaultSessionState()`，
  并在读取边界补默认时采用 **MERGE**：`{...parsed.data, cast: parsed.data.cast ?? {}}` —— 若直接替换，
  旧行会**丢掉时钟与变量**，这正是补默认必须"合并"而非"覆盖"的原因（`innerClock` 先例，**不加迁移行**）。
- **为什么这是"实时"、而不是"再存一份快照"**，四条：
  1. 调度器与面板读的是**此刻**，而一次干预会**改变它**；
  2. 它**必须随时钟一起回滚** —— 而回滚的单位正是 `Session.state`，所以它**本来就该在**那个值里面；
  3. `SessionRefs.cast` 是**这一局的名册**（钉住版本），干预**不改名册**；
  4. `Checkpoint.castState` 是**某个时刻**的快照（存档时写入），还原时**不读**它 —— 实时状态是"现在"、
     快照是"当时"，两者都存在才有"读档回滚"可言（与 ADR-032 同一句话）。
- **它必须进入调度器的"理由词汇表"**：`muted` / `absent` 两个排除理由在 `admit` 里**最先**判定（早于
  "卡缺失"与各项上限）→ 被干预的成员**不占用发言名额**，也**永远不会被报成"已达上限"**；`absent` 优先于
  `muted`；对它的**具名指派**会被 `refused`，并**以干预本身为理由**。存下来的是**无语种事实**
  （`muted=true`、`absent=present(false)`），句子由 `session/scheduler-text.ts` 用**穷尽**函数渲染
  —— 存储事实、渲染语言（把 ADR-030 的边界用在数据上），**没有任何代码会把存下的字符串解析回去**。
- 影响面：`packages/schema`（`SessionState` 增可选字段；`CastStateSchema` 由 `checkpoint.ts` 移到
  `session.ts` 并原地 re-export，**以免 session ↔ checkpoint 形成模块循环**）、`apps/web/src/session/cast.ts`
  （纯转移：旧状态 + 编辑 → 新状态；撤销即把被替换的那个值写回）、调度器、`db/repository.ts`（读取边界
  补默认）、播放屏面板。
- 验收：`SessionState.cast` 往返存储；**在它之前写下的行仍能打开**（MERGE 补默认，时钟与变量不丢）；
  干预后调度器不再选中该成员，且排除理由**点名干预本身**（并有对照组：去掉干预后同一个人会被选中）；
  撤销后**存储行逐字节还原**（面板一步；以及存档回滚把它随时钟一起带回）。

# 时间线（ADR-036）

## ADR-036 · 分叉的血缘由子指向父、写在 `extensions` 里；原时间线上不放反向指针

- 状态：已定
- 背景：M1-M2 的验收是"**原时间线不受影响；新线引用一致**"。分叉要把一条祖先链复制到新会话，于是有两个问题：
  新线怎么记住自己从哪来，以及原线要不要记住自己分出去了谁。
- **决策一：血缘写在 `Session.extensions`**（`common.ts` 规则 1 允许的唯一非核心通道），三个扁平键
  `x-smarttavern.forked-from.session-id` / `.message-id` / `.checkpoint-id`，存的是**原时间线**的 id ——
  与 `versioning.ts` 的 `Lineage.parentId` **同一族：由子指向父**（ADR-010）。此外**每一行**都带
  `x-smarttavern.origin-id`（与 `packages/importers/src/identity.ts` **同一拼写**），于是"重映射"在库里是
  **可审计的**，而不只是可推断的。
- **决策二：原时间线上不放 `forks: []` 之类的反向指针**，三条理由：
  1. 验收那句话说的是**原会话的行**：若"分叉"要在原行上追加一个列表，它就成了**对必须保持不动的那条时间线的
     一次写入** ✗；两次并发分叉还会变成**丢失更新** ✗。
  2. 历史本来就处处**由子指向父**（`Message.parentId`、`Lineage.parentId`）—— 反向指针会成为唯一的例外。
  3. "哪些会话来自这一个"**可以由分叉推出来**，再存一份就是**一个可能与事实不符的缓存**。
- **"原时间线不受影响"是在字节上证明的**：测试用**原始 IndexedDB API** 逐行 dump 原会话拥有的每一行
  （sessions / messages / checkpoints / turnPlans），分叉前后 `toBe` 比较 —— **刻意不走 repository**，因为它会把
  未知字段解析掉，而那种字段正是坏分叉会弄坏的东西。`forkSession` **只写新行、在一个事务里**。
- **pin 逐字复制（id 与 version 都复制），绝不重新解析** —— 这是 M1-I2 的发现（"版本号不是身份"）在分叉上的
  同一课：当世界有两个版本、而原会话钉的是 v1 时，按"最新"重新解析会**静默换掉**角色与规则。有用例钉住。
- **随行与不随行**：随行＝pin、`schedulerMode`、切点之前的链、**切点那一刻的整个 `SessionState`（无别名共享）**、
  `initialClock` = 切点时钟（分叉从被切处开始）、以及**被复制链仍能回答的**存档点。不随行＝切点之后的消息与
  链外兄弟、切点之后的存档点（它们的位置在新线里不存在）、`turnPlans` 行（被复制的消息保留 `meta.turnPlanId`，
  它诚实指向"当时那条时间线里"的计划）、原标题（由调用方拼、按**码点**夹到 schema 的 200 字上限），以及
  **原会话自己的 `extensions` 包**（外来插件包里可能存着我们无法重映射的原 id）。
- 验收：原会话的行分叉前后**逐字节相同**；新线所有行都是新 id 且不与原线冲突；新线的链等于原线到切点为止的链、
  `headMessageId` 指向切点的副本；血缘三键指回原线；切点不是链尾时**拒绝且什么都不写**（这是**可达**状态：
  head 指向一个已被删除的行，与 M1-S2 的"只删叶子"相接）。

# 可选性与默认值（ADR-037）

## ADR-037 · 时间推进与多角色发言调度是**一个应用级开关**、默认关闭；关闭时必须同时不注入时间块

- 状态：已定（首次人工验收的第 ⑥ 条拍板；落地在验收修复的 C 阶段）
- 背景：首次人工验收提出"时间推进与多角色发言调度建议写成可选的插件，先不急着跑通，**验证完正常的一对一 RP 之后再开发**"。而当时两者都是**常驻**的，且入口各只有一个：
  - 时间是内置预设里的一个 **PromptBlock**（`apps/web/src/chat/builtin-content.ts` 的 `BUILTIN_PRESET.blocks`，id `builtin-world-clock`，`budget: { priority: 'required' }`，内容是"当前时间：{{date}} {{time}}（{{segment}}）"）；推进时钟的**唯一**发起路径是播放屏的时间控件（`apps/web/src/app/routes/play.tsx` 的 `TimeControls`）→ `apps/web/src/state/chat-store.ts` 的 `advance`。**注意：世界卡里 `timeRhythm.implicitAdvance` / `advanceEveryTurns` / `stepMinutes` 那套"每回合自动推进"全仓没有任何引擎或 store 读取它** —— 未接线。
  - 调度是 `apps/web/src/session/scheduler.ts` 的 `planTurn`（纯函数），由 `apps/web/src/state/chat-store.ts` 三处调用并把 `TurnPlan` 落库。
- 决策：**一个开关**，住既有的 `settings` 集合（`theme` / `provider.*` 的同一条通道），键 `feature.timeAndScheduling`；**行缺席＝关闭** —— 与"在这台设备上记住解锁"同一形状（可选功能默认关闭 ⇒ 缺席即关闭）；`docs/02` §7 的十八个集合清单不动，也**不往会话行上加字段**。
- **关闭必须同时成立三件事**，缺一条就只是"半关"，而半关正是本项目最忌讳的**一个决定有两个答案**：
  1. **不推进**：播放屏不再提供推进（`TimeControls` 不渲染，或 `advance` 在关闭时直接返回）。今天要覆盖的推进入口**只有用户手动那一个**；**将来接线 `timeRhythm.*` 的自动推进时，它必须先问这个开关** —— 这一句是写在这里的**约束**，不是实现。
  2. **时间块不参与组装**：关闭时把 `BUILTIN_PRESET.blocks` 里 id 为 `builtin-world-clock` 的那一块**滤掉**，并且**不再传 clock**（`{{date}}`/`{{time}}`/`{{segment}}` 的唯一来源是 `promptContext` 的 `clock` 参数，注入点只有 `apps/web/src/chat/send-turn.ts` 的 `composeTurn(...)` 那一处）。**调 `priority` 没有用**：`required` 在 core 的裁剪里永不丢弃，且 app 内**没有任何**按 block id 或按 `'required'` 的分支（`priority` 的消费方全在 `packages/core` 的预算器里）—— 所以**只能过滤**。这也是"关掉时间必须连注入一起关"的机械理由：只关推进、不关注入，模型仍会读到时间，用户看到的行为**没有变化**。
  3. **调度器不参与发言决定**：`chat-store` 那三处 `planTurn` / `writeTurnPlan` 在关闭时跳过，走单发言者直发。**`planTurn` 本身不改**（它仍是纯函数）—— 于是"上限被硬性强制执行"这条验收条文仍由它自己保证，只是**只在开启时适用**。
- **为什么是应用级、而不是按会话**：集合清单已冻结成"十八个、逐字"，而"这个功能开着吗"是**用户的能力与偏好**，不是"这一局的设定"；按会话存会变成**第二处存放同一个决定**的地方（ADR-030 / ADR-033 已经裁过这件事）。**按会话覆盖记为将来的方向**，本次不做。
- **为什么默认关闭**：用户要的就是"先只跑一对一"。默认打开等于把一整套**行为**塞给只想一对一的人。代价写明白：**已存在的库升级后也是关闭状态**（那一行本来就不存在），这是有意的，且设置页一键可开。
- **"写成插件"落实为一个开关，而不是一套脚本机制**：可分享文件里能携带的"行为"就是**换了名字的脚本**（ADR-033 的同一句话）。因此这个开关**不进 `.stpack`、不随包分享** —— 它描述的是**本机这位用户**想让应用参与多少，而不是某份内容自带的规则。
- 影响面：`apps/web/src/chat/builtin-content.ts`（时间块是否参与组装）、`apps/web/src/chat/send-turn.ts`（唯一的注入点）、`apps/web/src/state/chat-store.ts`（`advance` + 三处 `planTurn`/`writeTurnPlan` 调用）、`apps/web/src/app/routes/play.tsx`（`TimeControls`）、`apps/web/src/db/repository.ts`（一对读写 helper，比照 `readThemeSetting` / `writeThemeSetting`，"一行一个 key"）、设置页（一个复选框，比照外观那一节）、`packages/i18n`（文案）。**不加迁移行**：缺席即关闭，读取处就是判定处（与 ADR-032 / ADR-034 同一条规则）。
- 验收：**两组对照** —— 关闭时请求里**不含时间块**（断言组装出的 system 内容里没有那个时间块的字样）、时钟不动、一遍回合只有一名发言者；开启时行为与开关引入**之前逐字节相同**，证据是**既有的时钟/调度用例原样通过、不改一条断言**；旧库无需迁移即可打开；开关可来回切换且**可撤销**。
