## 1. 架构总览

整体是一条**单向依赖**的纵向分层，目标是让"角色扮演引擎"完全独立于界面，从而
同时服务 Web / 桌面 / 移动三种形态，并为未来的 CLI、HTTP API、插件留出入口。

```
┌──────────────────────────────────────────────────────────────┐
│  UI 层（apps/web + apps/desktop 壳）                          │
│  三段式向导 · 扮演界面 · 立绘区 · 时间轴 · 调度面板 · 设置      │
├──────────────────────────────────────────────────────────────┤
│  应用层（packages/core/app）                                  │
│  用例编排：CreateWorld / CreateCharacter / StartSession /     │
│           AdvanceTime / Revisit / ExportPackage ...           │
│  领域聚合根：World, Character, Session, Checkpoint, Package    │
├──────────────────────────────────────────────────────────────┤
│  引擎层（packages/core/engine）                               │
│  PromptComposer · ContextBuilder · MemoryManager ·            │
│  ToolRuntime · DiceEngine · RuleResolver · ImagePipeline ·    │
│  TurnScheduler · TimeEngine · SessionEngine（消息树 + 存档）    │
├──────────────────────────────────────────────────────────────┤
│  契约层（packages/schema）                                    │
│  冻结的数据契约：实体 schema、包格式、JSON Schema 导出、迁移     │
├──────────────────────────────────────────────────────────────┤
│  Provider 层（packages/providers + packages/storage）          │
│  LLMProvider · ImageProvider · StorageAdapter · AssetStore ·  │
│  Importer/Exporter                                           │
├──────────────────────────────────────────────────────────────┤
│  数据层                                                       │
│  IndexedDB/SQLite（结构化数据） + OPFS/文件系统（资源）         │
└──────────────────────────────────────────────────────────────┘
```

**三条不变式**

1. `packages/core` 不得依赖 DOM / 浏览器专有 API，也不得直接 import 具体 Provider。
2. 所有跨模块的数据结构定义在 `packages/schema`，由 Zod 定义并导出 TypeScript 类型与
   JSON Schema（供第三方工具与包格式校验复用）。
3. **AI 只能"请求"，不能"写入"**：一切状态变更经由 ToolRuntime 校验后由本地执行。

## 2. 关键技术决策

### D1：不 fork SillyTavern，只兼容其数据格式

| 方案 | 成本 | 风险 | 结论 |
| --- | --- | --- | --- |
| A. fork 本体改造 UI | 高 | 上游迭代快，长期 merge 痛苦；AGPL 传染 | 否 |
| B. 自建前端 + 兼容格式 + 可选接 ST 为 Provider | 中 | 需自维护 prompt 引擎 | **采用** |
| C. 完全重写、不兼容 | 中 | 失去存量用户与角色卡生态 | 否 |

### D2：前端框架

**React 19 + TypeScript + Vite**（ADR-017，取代 ADR-005 的 Svelte 5）。
选型理由：本项目 UI 主体是"Zod 驱动的结构化表单 + 长列表虚拟化 + 拖拽排序"（世界编辑器 /
角色卡 / 世界书 / 规则速查 / 导出面板），React 生态在 `react-hook-form` +
`@hookform/resolvers/zod`、TanStack Virtual、dnd-kit 等方向有互为配套的成熟方案，胶水代码最少；
本地优先、无 SSR/SEO 诉求，SPA 已足够。
配套：TanStack Router（路由）、Zustand + Dexie liveQuery（状态与数据）、
Tailwind CSS v4 + Radix Primitives（样式与无障碍）、react-i18next（i18n）。
要求不变：UI 组件与业务状态分离，业务状态放 core，UI 只订阅。

### D3：多端方案

| 形态 | 方案 | 说明 |
| --- | --- | --- |
| Web / PWA | Vite 静态构建 + PWA 插件 | 一等公民，可离线使用 |
| 桌面 | **Tauri 2** | 体积小；Rust 侧提供无 CORS 限制的 HTTP 与文件系统访问 |
| 移动 | 响应式 PWA 优先；后续 Tauri 2 移动端 | 避免过早承担原生构建链成本 |

### D4：存储方案

**`StorageAdapter` 接口，MVP 用 IndexedDB（Dexie）全端统一，V1 为桌面端增加 SQLite 实现。**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| IndexedDB（统一） | 一套代码全平台 | 备份/导出需自造、大 blob 管理弱 |
| SQLite（Tauri plugin） | 事务强、迁移清晰、备份简单 | Web 端需 wa-sqlite/OPFS，双实现 |
| 纯文件 JSON | 易读易备份 | 并发与查询差，大数据量卡顿 |

结构化数据走 adapter，图片等大文件走 AssetStore（内容寻址 + 独立文件），数据库只存元数据与哈希。

### D5：是否需要后端

默认不需要（BYO-Key 前端直连）；提供**可选轻量代理**解决 Web 端 CORS 与密钥暴露；
桌面端通过 Tauri Rust 侧发起请求并可用系统 keyring。不做官方云服务。

### D6：生图一致性策略（分级）

| 级别 | 做法 | 成本 | 一致性 |
| --- | --- | --- | --- |
| L1 | 冻结 base prompt + 固定 seed，仅替换表情/服装标签 | 极低 | 中 |
| L2 | 以立绘为参考图做 img2img / inpaint | 低 | 较好 |
| L3 | Reference-only / IP-Adapter / ControlNet 锁角色与构图 | 中 | 好 |
| L4 | 专属 LoRA（用户自备） | 高 | 最好 |

首发实现 L1，L2/L3 通过 ComfyUI 工作流模板提供，L4 只做参数绑定。

### D7：规则内容的版权边界

内置仅开放许可内容（如 D&D 5e SRD，CC-BY-4.0，需署名）；其他规则只提供框架与结构示例，
内容由用户导入；规则包必须带 `license` 与 `source`，UI 必须展示。

### D8：分享格式先行冻结

包格式（`docs/04-分享格式规范.md`）是整个系统的"数据血管"：存档、分享、备份、跨端迁移、
第三方工具互操作都走它。**先冻结格式并写出往返测试，再写任何编辑器 UI。**
格式由 `packages/schema` 的 Zod 定义生成 JSON Schema，作为唯一事实来源。

### D9：身份是会话的属性，不是卡片的属性

角色卡不区分玩家 / 卡司；`Session.refs.playerCharacter` 指定玩家角色，其余为卡司。
好处：一张卡可在不同会话扮演不同角色；导入导出无需身份映射；用户的干预能力对所有卡一致可用。

### D10：发言调度必须由本地计算，AI 只能提议

评分、排序、上限、冷却全部在本地 `TurnScheduler` 完成；"AI 决定"模式下 AI 的输出也只是
一份**顺序提案**，仍需通过本地约束校验后才生效。这样调度结果可解释、可复现、可调参。

### D11：时间必须显式建模

时间不是叙述里的形容词，而是 `WorldClock`（唯一真值：从纪元起的分钟数）+ 历法映射 +
`Checkpoint` 中的快照。所有与时间相关的行为（世界书条件命中、日程触发、倒计时、
记忆时间戳、上下文注入）都从时钟派生。

## 3. 代码组织（pnpm workspaces）

```
smarttavern/
├─ apps/
│  ├─ web/                 # SPA / PWA，唯一的 UI 实现
│  └─ desktop/             # Tauri 2 壳：挂载 web 的 UI + Rust 侧 HTTP（src-tauri/）
├─ packages/
│  ├─ schema/              # 【冻结契约】Zod 实体定义 + JSON Schema 导出 + 迁移
│  ├─ core/                # 领域模型 + 引擎（无 DOM 依赖）
│  │  ├─ domain/           # World, Character, Session, Checkpoint, Package ...
│  │  ├─ engine/           # PromptComposer, ContextBuilder, MemoryManager,
│  │  │                    # ToolRuntime, TurnScheduler, TimeEngine,
│  │  │                    # DiceEngine, SessionEngine, ImagePipeline
│  │  ├─ ports/            # 接口：LLMProvider, ImageProvider, StorageAdapter ...
│  │  └─ app/              # 用例编排
│  ├─ providers/           # LLM / 图像 Provider 适配器
│  ├─ storage/             # IndexedDB / SQLite / AssetStore 实现
│  ├─ rules/               # 骰子、判定、检索 + 内置规则包数据
│  ├─ packages/            # .stpack 打包 / 解包 / 校验（纯逻辑，可被第三方复用）
│  ├─ importers/           # SillyTavern / Risu / Tavern 导入导出
│  ├─ ui/                  # 共享组件（无业务逻辑）
│  └─ i18n/
├─ docs/
└─ tools/                  # schema 生成、规则包校验、示例内容生成
```

工具链：pnpm + Biome（lint/format）+ Vitest + Playwright + msw + VitePress。
依赖方向强制：`schema` ← `core` ← `{providers, storage, rules, packages, importers}` ← `apps/*`。
可用 ESLint/Biome 的 `no-restricted-imports` 固化这条约束。

**桌面壳怎么"复用 web"（M0-T8 落地，ADR-025）**：`apps/web` 导出一个挂载函数
（`mountApp(root, { transport })`），UI 与状态层**只有这一份**；`apps/desktop` 是独立的一份
前端产物，它做的事只有两件 —— 调用那个挂载函数，并注入一个**由 Rust 承载的 `FetchLike`**
（`src-tauri/` 里的 `llm_stream` / `llm_cancel`）。因此桌面端不是"另写一遍 UI"，也不是在 web 里
到处 `if (isTauri)`；差别**只在注入的那一个参数**上。Rust 侧只搬字节（连 SSE 都不解析），
`packages/providers` 的适配器一行都不用改。

### 4.1 M0-T1 冻结的补充约定（§4 草案未覆盖的部分）

§4 是接口**草案**，实现时留下两类空白，M0-T1 一并冻结。

**① §4 引用过、但从未定义的类型**（唯一事实来源是 `packages/schema/src`）：

| 类型 | 位置 | 冻结内容 |
| --- | --- | --- |
| `SamplingParams` / `Partial<SamplingParams>` | `common.ts` | `temperature` 与 `topP` 必需，其余可选；`Partial` 供角色卡只覆盖单项 |
| `Region` / `Faction` | `entities/world.ts` | §4 的 `WorldData` 引用了它们却没定义，取最小可用形状 |
| `MemoryEntry` | `entities/memory.ts` | 从 §7 的 `memories` 集合反推补齐（含 `atMinute`） |
| `WorldbookEntry` | `entities/worldbook.ts` | 从 §7 的 `worldbookEntries` 反推补齐 |
| `CharacterData.stExtensions` | `entities/character.ts` | 存放他人 ST 脚本写进卡片的 `extensions`，键名**不受** `x-` 限制，导出时原样写回（docs/04 §10 的往返要求） |

**② 插件扩展点**（`packages/schema/src/plugins.ts`；M0 **只冻结接口，不实现加载器**）：

| 扩展点 | 载体 | 规则 |
| --- | --- | --- |
| 实体附加数据 | 每个实体的 `extensions` | 键必须形如 `x-<命名空间>[.路径]`，值必须是 JSON |
| 新增枚举成员 | `openEnum()` 生成的开放枚举 | 已知成员 + `x-<命名空间>` 成员仍可通过校验；**固有协议语义**的枚举保持封闭（如 `Message.role`、`ToolCall.status`） |
| 插件自身声明 | `PluginManifestSchema` / `PluginStateSchema` | `id` 即命名空间；声明 `apiVersion`、`permissions` 与 `contributes`，由未来的加载器决定是否授予 |
| 工具 / Provider / 规则包 / 语言包 | `core/ports` 与纯数据 | 一律按 id 注册；规则包与预设永远只是数据，**绝不执行代码**（HANDOFF §9.3） |

**③ 未知字段一律「剥除、不报错」**：所有实体使用普通 `z.object`（Zod 默认 strip）。
这是 HANDOFF §4.1 第 5 条（读方必须忽略未知字段）与 JSON 往返字节稳定的实现方式。
插件需要长期保存的数据**必须**放进 `extensions`，放在其他位置会在下一次往返中消失。

> M0-T1 落地的实体清单：`world` / `character` / `session` / `message` / `checkpoint` /
> `agenda` / `memory` / `asset` / `turn` / `worldbook`（均在 `packages/schema/src/entities/`）。

> 包的 manifest schema 见 `docs/04-分享格式规范.md`；实体 schema 与 JSON Schema 由
> `packages/schema` 用 Zod 生成，禁止手写两份。

## 5. 引擎层设计

### 5.1 Prompt 引擎（PromptComposer）

参照并简化 SillyTavern 的 Prompt Manager：**一切进入模型的内容都是有序的 Prompt 块**。

```ts
interface PromptBlock {
  id: string;
  name: string;
  role: 'system' | 'user' | 'assistant';
  content: string;                 // 支持宏
  enabled: boolean;
  position: 'pre_history' | 'in_history' | 'post_history';
  depth?: number;
  order: number;
  budget?: { share?: number; priority: 'required' | 'high' | 'normal' | 'optional' };
  conditions?: { keywords?: string[]; minTurns?: number; timeOfDay?: string[] };
}
```

**装配顺序**（ContextBuilder 职责）：

```
系统指令（角色 system_prompt + 会话 system + 调度指令）
  → 世界设定摘要（含历法与当前时间常识）
  → 【当前时间】年月日 + 时段（硬注入，P0）
  → 世界书命中条目（关键词 / 时间条件触发）
  → 角色卡字段（description / personality / scenario / mes_example）
  → 玩家角色信息（{{user}} 对应的卡）
  → 长期记忆（按重要度与时间新旧）
  → 滚动摘要
  → 最近 N 轮原文
  → 本轮发言计划（TurnPlan：谁来说、说什么方向、条数预算）
  → 工具定义与结果
  → 当前用户输入
```

**宏系统**：`{{char}}` `{{user}}` `{{time}}` `{{date}}` `{{segment}}`（时段）
`{{scene.location}}` `{{world.name}}` `{{random::a,b}}` `{{pick::...}}`
`{{getvar::hp}}` `{{setvar::hp::10}}` `{{roll::2d6}}` `{{speaker}}` `{{round}}` + 自定义宏插件。

**Token 预算**：总预算 = 模型上下文长度 − 预留输出长度。按块优先级从低到高裁剪
（optional → normal → high；required 永不裁剪，超限则明确报错并给出建议）。
优先用 Provider 的计数接口，否则用近似分词器并缓存。

### 5.2 上下文与记忆（MemoryManager）

| 层级 | 内容 | 触发 |
| --- | --- | --- |
| L0 即时 | 最近 N 轮原文 | 总是 |
| L1 场景摘要 | 当前场景的压缩叙述 | 每 N 轮或超预算 |
| L2 滚动摘要 | 更早历史的递进摘要 | 超预算时合并 |
| L3 长期记忆 | 结构化条目（事件 / 关系 / 事实 / 承诺），**带时间戳** | AI 抽取 + 用户确认 |
| L4 世界书 | 关键词与时间条件命中的设定条目 | 匹配触发 |
| L5 检索 | 全库全文 / 向量检索 | 按需（工具调用） |

**摘要策略**：用便宜模型做增量摘要（旧摘要 + 新 N 轮 → 新摘要），记录被摘要的消息区间与
**发生的时间范围**，便于溯源与"回忆某天发生了什么"。

**世界书匹配**：Aho-Corasick 多模式匹配；支持主/次关键词、正则、概率触发、扫描深度，
以及**时间条件**（`timeOfDay` / `afterMinute` / `withinDays`）。命中详情写入消息元数据，
UI 可解释"为什么这条设定被注入"。

### 5.3 工具运行时（ToolRuntime）

让 AI 通过结构化调用操作应用状态，而不是靠自由文本描述，从而收敛幻觉与格式错误。

| 工具 | 作用 |
| --- | --- |
| `roll_dice(expr, reason)` | 掷骰，本地引擎执行 |
| `lookup_rule(pack, query)` / `get_rule_section(id)` | 检索规则原文 |
| `read_sheet(target, path)` / `update_sheet(target, path, value)` | 读写角色数值 |
| `adjust_resource(target, key, delta)` | HP / 理智 / 资源增减，受上下限约束 |
| `set_scene(title, location)` | 更新场景（时间不在此处改） |
| `set_emotion(character, emotion)` | 驱动颜绘切换 |
| `add_memory(text, keywords, importance, atMinute)` | 写入待确认记忆 |
| `request_image(character, expr, outfit, scene)` | 排队生成立绘 / 差分 |
| `save_checkpoint(label)` | 自动打点 |
| `propose_world_patch(patch)` / `propose_character_patch(patch)` | 设定变更提案 |
| `advance_time(amount, unit, reason)` | **请求推进时间**（受会话策略约束，见 5.7） |
| `schedule_event(title, atMinute, actors, secret)` | 登记日程事件（提案） |
| `add_deadline(label, dueMinute)` | 登记倒计时（提案） |
| `propose_turn_order(characterIds)` | 在 AI 调度模式下提出发言顺序（仍需本地校验） |
| `narrate_npc(name, lines)` | 引入新 NPC（需确认后入库） |

**执行模型**：工具调用 → JSON Schema 校验 → 领域规则校验（资源上下限、骰子语法、
时间推进策略）→ 本地执行 → 结果回灌 → 继续生成。所有调用写入消息元数据，可审计可撤销。

**降级策略**：① 原生 function calling → ② 结构化输出（JSON Schema 约束） →
③ 文本协议 `<tool name="...">{...}</tool>` 解析。三级都失败时**不静默忽略**，
提示用户并可重试。无论哪一级，最终执行权都在本地。

### 5.4 骰子与规则引擎（DiceEngine / RuleResolver）

- **骰子表达式**：`NdM`、`kh/kl`、`dh/dl`、`!` 爆炸、`r` 重投、修饰符、括号、
  比较（`d100 vs 65`）。
- **规则适配**：D&D 5e（d20 + 优势/劣势、DC 表）、CoC 7e（d100、奖励/惩罚骰、成功等级）、
  Fabula Ultima（双属性骰池、机遇/灾害）、Cyberpunk RED（d10 爆炸、DV 表、SP 减伤）、
  通用 d20 / d100。
- **可复现**：记录表达式、种子、结果、时间（含世界时钟）、发起者。
- **权威性**：结果必须来自本地引擎；AI 只能"申请掷骰"。
- **公式求值**：白名单求值器（算术 + `floor/ceil/min/max` 等纯函数），绝不 eval。

### 5.5 图像流水线（ImagePipeline）

```
视觉档案 + 差分矩阵选择
   → 提示词拼装（base + 表情 + 服装 + 场景 + 风格 + 负面，纯函数、快照测试）
   → 参数合并（模型 / 采样 / 尺寸 / seed 策略）
   → 任务入队 → Provider 提交 → 轮询或订阅进度 → 下载 → 存储
   → 内容寻址去重 → 缩略图 → 绑定到角色 / 会话
```

- **差分生成**：以立绘为基准，仅替换表情 / 服装标签，复用同一 seed（D6 的 L1）；
  或调用 img2img / inpaint 工作流（L2/L3）。
- **缓存**：`hash(prompt + params + provider + model)` 命中直接复用，避免重复花钱。
- **任务队列**：并发上限、指数退避重试、可取消、完成通知。
- **自动切换**：由 `set_emotion` 或本地关键词规则触发。

### 5.6 发言调度器（TurnScheduler）

**职责**：决定"这一轮谁说、按什么顺序、每人几条"，并输出可解释的 `TurnPlan`。

**默认评分公式（规则模式）**

```
score(c) = w1 * (desire / 100)
         + w2 * (ability / 100)
         + w3 * addressedBonus(c)      // 被用户/上一位发言者点名
         + w4 * keywordRelevance(c)    // 与场景/最近文本的关键词相关度
         + w5 * roleMatchBonus(c)      // 发言角色标签与场景类型匹配
         - w6 * recencyPenalty(c)      // 刚说过话的衰减
         - w7 * silenceRelief?         // 长期沉默的角色获得补偿（负号表示加成）
         + jitter(seed)                // 可复现的微小随机，避免僵化
```

默认权重（可被会话覆盖）：`w1=0.30, w2=0.25, w3=0.20, w4=0.10, w5=0.10,`
`recency=-0.25, silenceRelief=+0.10, jitter=±0.03`。

**硬约束（本地强制，AI 无法突破）**

- `maxSpeakersPerRound`（默认 3）：一轮最多几个角色发言
- `maxLinesPerRound`（角色卡字段，默认 2）：单人条数上限
- `cooldown`（角色卡字段）：刚发言者需要间隔的轮数
- 被 `muted` 的角色跳过；`present: false` 的角色不参与
- 玩家角色不参与排序

**三种模式**

| 模式 | 计算方式 |
| --- | --- |
| `user` | 用户手动指定顺序；调度器只负责校验约束并生成 TurnPlan |
| `rules` | 上述公式本地计算，UI 展示每个候选的分数与理由 |
| `ai` | 由 LLM 输出顺序提案（`propose_turn_order`），经本地约束校验后生效 |

**可解释性**：TurnPlan 中的 `reasons` 必须能说明每条加/减分来源，
UI 在调度面板中以自然语言展示（"因为被点名 +0.2；因为上轮刚发言 -0.25"）。

**与生成的关系**：TurnPlan 注入 prompt，AI 按计划产出；若 AI 未遵守计划，
不强行截断，而是在 UI 上标记偏差并允许用户重排（保持创作自由度）。

### 5.7 时间引擎（TimeEngine）

**数据**：`WorldClock`（`EpochMinute` 唯一真值 + `Calendar` 映射）+ `AgendaEntry[]` + `Deadline[]`。

**核心操作**

| 操作 | 说明 |
| --- | --- |
| `advance(delta)` | 推进时钟；返回途中触发的日程、到期的倒计时、跨越的时段 |
| `setTime(minute)` | 直接设定（仅用户可操作，需确认） |
| `display(minute)` | 历法映射 → "第三纪 1287 年 霜月 12 日 · 黄昏" |
| `segmentOf(minute)` | 返回时段（晨/昼/昏/夜），供世界书条件与上下文注入 |
| `fireDue(now)` | 取出 `atMinute <= now` 的 pending 日程，标记 fired 并生成提示 |
| `repeatHandling` | 重复日程按 `repeatEveryMinutes` 顺延下一次 |

**推进策略**（`timeRhythm` + 会话设置）

| 来源 | 默认策略 |
| --- | --- |
| 用户手动 | 直接生效 |
| 隐式（每 N 轮） | 默认关闭；开启后每 N 轮按 `stepMinutes` 推进 |
| AI `advance_time` 请求 | 三选一：`auto` / `ask`（默认）/ `deny`；大步长（超过 1 天）强制 `ask` |

**副作用链**（一次推进要做的事，按顺序）

```
1. 计算新时刻与跨越的时段
2. 取出到期日程 → 生成系统提示或插入待播事件
3. 检查倒计时 → 过期则触发提醒
4. 重新评估时间条件世界书（可能有条目失效或生效）
5. 更新 SessionState.clock
6. 写入自动存档（推进前后各一个点）
7. 在下一轮 prompt 中注入新的时间描述
```

**与存档的关系**：`Checkpoint.state.clock` 是权威快照；读档即回滚时钟。
不允许"时间回退但状态不回退"，避免状态分裂。分叉时以存档点的时钟作为新线的起点。

**与 TRPG 的关系**：战斗内使用 `innerClock`（轮 / 回合），叙事时钟挂起；
战斗结束时把 `innerClock` 折算为叙事时间增量（如 10 轮 = 1 分钟）。

| 集合 | 关键字段 | 索引 |
| --- | --- | --- |
| `worlds` | id, name, headVersion, tags, createdAt | name |
| `worldVersions` | id, worldId, version, data(含 calendar/timeRhythm), lineage | (worldId, version) |
| `characters` | id, name, headVersion, tags | name |
| `characterVersions` | id, characterId, version, data(含 voice/visual), lineage | (characterId, version) |
| `worldbooks` / `worldbookEntries` | id, worldId, keywords, content, priority, position, depth, probability, **conditions(timeOfDay/afterMinute/withinDays)**, enabled | (worldId), keywords |
| `promptPresets` | id, name, version, blocks[] | name |
| `rulePacks` | id, name, system, version, license, source, content | system |
| `sessions` | id, title, refs(**playerCharacter**, cast[]), schedulerMode, headMessageId, createdAt | createdAt |
| `messages` | id, sessionId, parentId, role, speakerId, kind, content, emotion, toolCalls, meta | (sessionId, parentId), createdAt |
| `checkpoints` | id, sessionId, label, messageId, auto, state(**clock/innerClock/deadlines**), agendaStatus, summary, castState | (sessionId, createdAt) |
| `agenda` | id, sessionId, title, atMinute, repeatEveryMinutes, actors, secret, status, source | (sessionId, atMinute, status) |
| `turnPlans` | id, sessionId, round, mode, entries[], excluded[], overriddenByUser | (sessionId, round) |
| `memories` | id, scope, targetId, text, keywords, importance, **atMinute**, status, sourceMessageId | (scope, targetId), atMinute |
| `assets` | id, hash, kind, mime, width, height, bytes, path, thumbId, refCount, meta | hash（唯一） |
| `jobs` | id, provider, kind, params, status, assetId, error, createdAt, finishedAt | status |
| `providers` | id, kind, baseUrl, apiKeyRef, models, enabled, options | kind |
| `settings` | **id**(存配置键), value | — |
| `migrations` | **id**(存版本号), appliedAt | id |

**约定**：时间戳为毫秒；`data` 字段可 JSON 序列化；schema 带 `schemaVersion`，
升级走迁移脚本并保留备份。`personas` 集合自 v0.2 起移除（身份改为会话属性）。

**预设是扁平实体（别去找版本集合）**：`promptPresets` 的行**直接带** `blocks[]` 与 `version`，
不是 `worlds` / `characters` 那样的 head+version 两个集合 —— `docs/04` §2 的载荷同样写作
`PromptPreset[]`（而 worlds 明确写作 `WorldVersion[]`）。因此 ADR-010 的"不可变版本"对预设**不适用**，
历史可复现由 `MessageMeta.promptSnapshotId`（每条消息存下它当时用的那份装配）保证；
预设更像一份**设置**：用户会一直调，`version` 只是显示与迁移用的计数器（ADR-029）。

**行寻址**：`settings` 与 `migrations` 的主键**就是 `id`**（分别存放配置键与版本号），
其余集合本来就以 `id` 为主键。因此端口只需要**一条**寻址规则，不为这两张本地内部表引入
泛化的非 `id` 主键机制（ADR-022）。

**M0 已用的配置键**：`settings` 里 `id: 'llm.provider'` 存 `{ baseUrl, apiKey, model }`，
即 BYO-Key 的落点（ADR-027）。它只是本地库的一行：**不进 `.stpack`、不进日志、不进
`Message.meta`、不进任何抛给用户的错误文本**。

> **排序陷阱（务必注意）**：`id` 是**字符串**，所以 `migrations.id` 里的版本号是它的
> **十进制字符串**。**不要按该键排序或做范围扫描** —— 字符串按字典序比较，`'10' < '9'`。
> 需要"最新已应用迁移"这类问题时，用 `migrations.appliedAt`。任何把数值停在 `id` 里的
> 集合都同理。

**消息树与分叉**：消息是树（`parentId`），支持重生成（同父多子）、编辑（新分支）、
回溯（移动 `headMessageId`）、分叉（从任意节点复制祖先链创建新会话）。
显示路径 = 从 `headMessageId` 上溯到根再反转；长会话需缓存路径或维护 `depth`。

**资源生命周期**：内容寻址 `hash = sha256(bytes)`；`refCount` 由引用关系维护；
被存档包或检查点引用的资源不可删除；缩略图生成时一并产出；清理需用户确认。

## 10. 安全与隐私

- **API Key**：桌面存系统 keyring；Web 用 WebCrypto 以口令派生密钥加密后存 IndexedDB；
  **绝不进入导出包与日志**。
- **网络**：只与用户显式配置的 Provider 通信；应用自身不发送遥测。
- **CORS / key 暴露**：Web 直连存在 key 进入浏览器内存的风险，文档明确警示并提供自建代理方案。
- **XSS**：角色卡、世界书、消息一律转义；Markdown 渲染使用白名单配置，禁用原始 HTML。
- **包导入安全**：校验 ZIP 路径穿越、条目类型、单文件与总大小上限、SHA-256；
  JSON 仅作数据解析，绝不执行脚本；拒绝 `../` 路径与绝对路径。
- **CSP**：生产构建启用严格 CSP；Tauri 侧限制可访问域名白名单。
- **内容分级**：默认关闭 / 不提供敏感内容策略，由本地开关控制（关闭 / 本地过滤 / Provider 过滤）。

## 13. 需要先冻结的接口（动工前）

这 8 项做成 `packages/schema` 与 `packages/core/ports` 下的独立文件，**先写类型 + Zod schema
+ 测试，再写实现**。它们是返工成本最高的地方。

| # | 契约 | 位置 | 为什么最贵 |
| --- | --- | --- | --- |
| 1 | `PackageManifest` + 包格式 | `schema/package.ts` | 存档、分享、备份、跨端迁移全依赖它 |
| 2 | 实体 schema（World / Character / Session / Message / Checkpoint） | `schema/entities/*.ts` | 决定数据库与迁移成本 |
| 3 | `StorageAdapter` 集合与字段 | `core/ports/storage.ts` | 换存储实现时的最大返工点 |
| 4 | `CharacterData` + `VoiceProfile` + `VisualBible` | `schema/entities/character.ts` | 导入导出与生图一致性的根基 |
| 5 | 世界时钟 + `Calendar` + `AgendaEntry` | `schema/entities/world.ts` + `entities/agenda.ts` | 事后补时间系统约等于重构存档与记忆 |
| 6 | `TurnPlan` + 调度权重配置 | `schema/entities/turn.ts` | 决定多角色体验与可解释性 |
| 7 | `LLMProvider` / `StreamEvent` | `core/ports/llm.ts` | 决定所有对话能力 |
| 8 | `ToolRuntime` 工具签名 + 降级协议 | `core/ports/tools.ts` | 决定 AI 能力上限与幻觉水平 |

**实现顺序建议**（与 `docs/06-开发任务拆解.md` 一致）：

```
schema（含包格式） → core/ports → core/engine 的纯函数部分（Prompt/Turn/Time/Dice）
  → storage 实现 → providers 实现 → app 用例 → UI
```
